## Security

### S1 — Google sign-in pre-account-hijack (Fixed)

`services/api/src/modules/google-signin.ts` `finishGoogleSignIn`: when the Google email matched an existing account, the Google identity was linked and the account marked verified. If that account had been created with email + password by someone who did not own the address (Qline does not verify emails, S3), the squatter's password and live sessions survived, so they kept access to the victim's account after the victim's first Google sign-in.

Fix (`google-signin.ts:96`): if the existing user's email is not verified, delete its `credential` (password) accounts and all its sessions before linking. Verified users are linked as before.

Test: `services/api/test/api.integration.test.ts` "Google sign-in removes an unverified password and old sessions before linking (audit 2026-11-21)". Verified: fails on the old code (`expected 200 to be 401`), passes with the fix.

### S2 — Platform admin without a verified email (Fixed)

`isPlatformAdmin` (`integrations/oauth.ts:120`) matched `QLINE_PLATFORM_ADMINS` by email only. Anyone could sign up with an admin's address (no verification, S3) and manage the platform OAuth apps. It now also requires `emailVerified === true`; `UserCtx.emailVerified` is set from the session (`core/context.ts:34`), and the four call sites in `modules/integrations.ts` pass the context. The existing platform-admin test now asserts 403 while unverified. Production check (read-only SQL): the owner account is verified through Google, so nothing changes for Jazz.

### Open items and recommendations

- **S3:** add email verification (Better Auth `emailVerification`) and password reset. Needs an email sender (the platform has none today). Until then S1/S2 fixes keep unverified accounts from gaining anything from a real owner.
- **S4:** consider adding `email.send` to `ALWAYS_ASK` (`packages/policy/src/index.ts:352`) when the triggering content came from an inbound email, or cap autopilot email to known contacts. The Terms (§4) now tell owners that autopilot actions are theirs and warn about injected instructions.
- **S5:** accept the key in a header (`x-qline-cron-key`) and keep the path form only for the scheduler that needs it.
- **S6:** shorter sessions or sliding refresh, and re-auth for export and owner-level changes.
- **S7:** add a per-org limit on AI and import routes to stop runaway cost.

### Verified as fine

- `npm audit`: 0 vulnerabilities; CI gate `scripts/audit-gate.mjs` unchanged.
- Secret scan of the repo: only test fakes.
- Android manifest: `allowBackup=false`, no cleartext traffic, receivers not exported. Session token in `flutter_secure_storage`.
- In-app updater checks APK SHA-256 and the signing certificate (docs/28).
- Row-level security on every tenant table; only auth/system tables (`account`, `session`, `user`, `verification`, `rateLimit`, `oauth_states`, `signin_requests`, `platform_oauth_apps`, `schema_migrations`) have none, and they are not reachable through tenant queries.
- Upload size and zip-bomb guards; Drive webhook token-hash check; Facebook calls use `appsecret_proof`; tokens sealed with AES-256-GCM (`core/secrets.ts`).
- Provider URLs are fixed hosts (no user-supplied URLs fetched server-side), so no SSRF path found.
- Production env has the expected variable names only; values not inspected.

## UI audit

Method: a temporary widget harness rendered 26 screens at 360 dp (the smallest common Android width) in dark, light, and dark at 1.3× text, with every Flutter layout error captured. Result: **no overflow or layout errors on any screen.** The harness was deleted before commit; the regressions are covered by `apps/mobile/test/audit_legal_test.dart`.

Fixed:

- **U1** Org setup: "Business" broke into "Busines/s" at 360 dp. Segments now show labels only (no icons) on one line (`screens/auth.dart`). Test fails on old code (60 px vs 40 px).
- **U2** Settings → Integrations subtitle listed old services. Now "Gmail, Drive, Calendar, Slack, Notion, GitHub and more".
- **U3** Sign-out confirmation said "You'll need your password", wrong for Google users. Now "You'll need to sign in again on this phone. Nothing is deleted." Same fix in "Sign out other devices".
- **U4** Signed-in devices: a disabled red "No other devices" button looked like an error. It is now a plain note. Test fails on old code.

Not fixed (minor): horizontally scrolling chip rows clip at 1.3× text without a fade hint.

### awesome-android-ui

[wasabeef/awesome-android-ui](https://github.com/wasabeef/awesome-android-ui) lists about 290 native Android View and Compose libraries. None can be used directly: Qline is Flutter. Used as a checklist of patterns instead, Qline already has the ones that matter for this app — skeleton loaders (`SkeletonList`), pull to refresh, bottom sheets, segmented buttons, charts, snackbars and empty states. **Recommendation: add no new UI libraries.** Each one adds maintenance and supply-chain risk for no user-visible gain.

## UX/UI round 2 (forui and GetWidget as references)

Jazz asked for a second UX/UI audit using [forui](https://github.com/duobaseio/forui) and [GetWidget](https://github.com/ionicfirebaseapp/getwidget) as references.

**The libraries.** forui (MIT, about 2,400 stars, pushed 2026-11-20, version 0.28) is a well-maintained, shadcn-style kit: about 40 widgets with their own theme system, built-in semantics, and a theme-wide haptic feedback setting. GetWidget (MIT, about 4,800 stars, version 7.0.2, last pushed 2026-05-24) is a large generic Material set: shimmer, intro screens, rating, carousel, sticky headers, toggles. **Neither was added as a dependency.** Qline already has its own design system (halo buttons, `QCard`, `Page2`, skeletons, sheets with drag handles, date and time pickers, 60 tooltips). Mixing in a second theme system would make screens inconsistent and add upgrade risk: forui is pre-1.0, and GetWidget updates slowly and is generic Material. They were used as a benchmark instead, and two patterns were borrowed: haptics (from forui's `FHapticFeedback`) and an edge fade on scrollable rows.

**Method.** Flutter's built-in accessibility guidelines (Android 48 dp tap targets, labelled tap targets, WCAG text contrast) ran on 25 screens with realistic data (dashboard, approvals, leads, tasks, integrations, sessions) in dark and light, and layout errors were caught at 1×, 1.3× and 2× text. Before trusting it, the contrast check was proven on a deliberately bad widget: the plain `evaluate()` call silently returned nothing, so the `meetsGuideline` matcher is used. The palette was also checked directly: every text colour is at least 4.5:1 on every surface in both themes, and borders are at least 3:1.

Found and fixed (each fix has a test that fails without it, in `apps/mobile/test/ux_guidelines_test.dart`):

- **U5** Home "At a glance" tiles overflowed at **1.3×** text, a common Android setting. The tile ratio now follows the text size.
- **U6** Lead inbox card header, Work task date/priority row, and Business agent cards overflowed at 2× text. They now ellipsize, wrap or grow.
- **U7** "Projects" (Work) broke onto two lines at 2×; segment labels now shrink to fit.
- **U8** Screen readers announced the Content Studio Drive card as an unlabelled button. `QCard` now merges its content into one labelled button, fixing every tappable card.
- **U9** No haptic feedback anywhere. `QButton` now gives a light impact for halo (the screen's one human decision) and a medium impact for destructive buttons; other buttons stay silent.
- **U10** (from round 1, item e) Clipped chip and segment rows gave no hint that they scroll. `EdgeFade` fades the edge only while more content is hidden (Lead inbox, Content Studio, Runs).

The permanent test runs the guideline sweep on 14 main screens in CI.

Not changed: the "New agent" card subtitle truncates at 2× text (no overflow, still readable as "New agent").

## Legal documents

- Source of truth: `apps/mobile/assets/legal/terms.md` and `privacy.md` (version 2026-11-21). The app shows them in Settings → Terms of service / Privacy policy and from the sign-in screen, including before sign-in and offline.
- `scripts/build-legal.mjs` generates `apps/site/{terms,privacy}/index.html` from the same files. CI runs `--check` and fails if they differ, so the website can never drift from the app again.
- Sign-in and sign-up show "By continuing / By creating an account you agree to the Terms of service and Privacy policy. You must be 18 or older." Both email and Google paths are covered.
- Settings → Delete account explains what is deleted and opens a pre-filled email request. Deletion itself is manual (within 30 days, as the policy says) because an owner's organisation needs a transfer-or-delete decision.

What the documents do to reduce legal exposure (not a guarantee — see below):

- Privacy: every data flow and connected service disclosed with its purpose; Qline as processor for customers' contacts and leads (the customer is the controller and must have a lawful basis); Google API Limited Use statement; international transfers (Singapore hosting, US and China AI providers); retention table; DPA rights and NPC complaint route; 72-hour breach notice (NPC Circular 16-03); 18+.
- Terms: beta "as is"; AI output not professional advice; owners responsible for autopilot actions and for approving posts and code; third-party terms (Meta Platform Terms etc.); anti-spam and acceptable use; official APK source only; source visible but not licensed; indemnity; liability cap (greater of 12 months' fees or PHP 5,000) with carve-outs for fraud, bad faith, gross negligence and wilful misconduct, which Civil Code Art. 1171 does not allow to be waived; Philippine law, Davao City courts after 30 days of informal resolution.

### Compliance checklist for Jazz

1. **Host the site** (`apps/site`) at a public URL, for example GitHub Pages, and put that URL in the Google OAuth consent screen and Meta app settings.
2. **NPC registration:** registration is mandatory at 250+ employees, 1,000+ individuals' sensitive personal information, or high-risk processing — and in every case for automated decision-making or profiling ([NPC Circular 2022-04](https://privacy.gov.ph/wp-content/uploads/2023/05/Circular-2022-04.pdf)). Lead urgency scoring may count. If not registering, file the sworn declaration of exemption the NPC asks for ([NPC notice](https://privacy.gov.ph/npc-to-issue-show-cause-orders-to-unregistered-businesses-handling-personal-data/)).
3. **DPO:** every controller needs one; as an individual operator, Jazz is the de facto DPO ([NPC](https://privacy.gov.ph/appointing-a-data-protection-officer/)). The privacy policy names Jazz.
4. **Breach plan:** notify the NPC and affected people within 72 hours ([NPC Circular 16-03](https://privacy.gov.ph/npc-circular-16-03-personal-data-breach-management/)). Keep a one-page runbook.
5. **Lawyer review:** have a Philippine lawyer review both documents before paid plans or wider launch. No document can guarantee that nobody will sue; these reduce the chance a claim succeeds.
6. **LICENSE:** decide whether the public repo should stay "all rights reserved" (current) or get a licence.
7. **Contact address:** the documents use chrono07g@gmail.com to match the Google consent screen. Change both together if that changes.
